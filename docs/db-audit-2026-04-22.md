## Executive Summary

The database is **structurally sound but architecturally confused**. The critical finding is a **split-brain storage problem**: the DB exists alongside a parallel GitHub JSON system, and most features use GitHub JSON as the live source of truth while the DB holds **stale or diverged copies of the same data**. Additionally, 37 of 47 SRB nights have totals that don't match their entry sums — a silent data integrity failure.

**The DB is only actively used for one thing: agent status.** Everything else is dead weight or a liability.

## 2. Issues Found

### 🔴 CRITICAL

#### C1: Foreign Key Enforcement Disabled
```
PRAGMA foreign_keys = 0  ← OFF by default, never enabled
```
`srb_entries` has a declared `FOREIGN KEY (night_id) REFERENCES srb_nights(id) ON DELETE CASCADE` — but it's never enforced. Deleting a night would leave orphaned entries, entries can be inserted with nonexistent `night_id`, and the `ON DELETE CASCADE` does nothing.

**Fix:** Enable `PRAGMA foreign_keys = ON` at connection open time in every route that opens the DB.

---

#### C2: SRB Night Totals Are Wrong — 37 of 47 Nights Drift
The `srb_nights.total` column is a **manually maintained denormalized sum** that has drifted from the actual sum of entries. This means the SRB Tips tab is displaying incorrect totals for 79% of nights.

Worst offenders:
| Night | Stored Total | Actual Sum | Drift |
|-------|-------------|------------|-------|
| srb-march-fri-mar-6 | $305 | $230 | **+$75** |
| srb-january-sat-jan-10 | $209 | $279 | **-$70** |
| srb-january-sun-jan-11 | $115 | $65 | **+$50** |
| srb-february-thu-feb-5 | $140 | $95 | **+$45** |
| srb-february-sat-feb-7 | $325 | $285 | **+$40** |

**Fix:** One-time data repair + add a trigger to keep totals accurate automatically.

---

#### C3: Split-Brain Storage — DB vs GitHub JSON Are Diverged

Most tabs read GitHub JSON, NOT the DB. But the DB has stale copies of the same data:

| Data | DB Rows | GitHub JSON | Diverged? |
|------|---------|------------|----------|
| `tesla_sessions` | 45 | 54 sessions | ✅ YES — DB missing 9 sessions |
| `artist_assets` | 16 | 21 assets | ✅ YES — DB missing 5 assets |
| `tasks` | 29 | 28 tasks (different structure) | ✅ YES — structure mismatch |
| `personal_tasks` | 0 | 19 tasks | ✅ YES — DB completely empty |

The DB tables for these features are dead weight — they consume space, cause confusion, and could mislead future developers into using them when the real data is in GitHub JSON.

**Fix:** Either (a) formally deprecate the dead tables with a comment, or (b) pivot to DB-first for all data (recommended long-term).

### 🟡 WARNING

#### W1: `agent_log` Route Is Statically Exported — Logging Is Broken
```typescript
// app/api/agent-log/route.ts
export const dynamic = "force-static";
// Returns { entries: [] } — always empty
// POST returns 405
```
The agent status log in the DB (`agent_status_log`, 12 rows) is written from other code paths, but the API route for reading/writing it from the frontend is completely non-functional. Agent history is invisible in Mission Control.

**Fix:** Remove `export const dynamic = "force-static"` and implement proper read/write using the DB.

---

#### W2: No Triggers — SRB Totals Can Never Stay Accurate
Without triggers, any INSERT/UPDATE/DELETE to `srb_entries` requires the calling code to also manually update `srb_nights.total`. This is what caused the C2 drift — it's a design flaw, not a data entry mistake.

**Fix:** Add INSERT/UPDATE/DELETE triggers on `srb_entries` that recalculate the parent night's total.

---

#### W3: Redundant Index on Primary Key
```sql
CREATE INDEX idx_state_agent ON agent_current_state(agent_name)
```
`agent_name` is the PRIMARY KEY of `agent_current_state`. SQLite automatically creates a B-tree index on primary keys. This index is **100% redundant** and wastes space on every write.

**Fix:** `DROP INDEX idx_state_agent`

---

#### W4: `agent_log` Route Conflicts With DB — Timestamp Index Useless Without Working Route
`idx_log_timestamp` on `agent_status_log(timestamp)` exists for fast time-range queries — but since the log route is broken and returns static empty data, this index serves no current purpose. Once the route is fixed (W1), it becomes useful.

---

#### W5: 147 SRB Entries With $0 Amount (31% of 471 rows)
```
$0 entries: 147
```
Nearly a third of all SRB entries have `amount = 0`. These may be legitimate "no tip" records for tracking dancer presence, or they may be data entry errors. Without a constraint, there's no way to distinguish them.

**Fix:** Investigate intent. If $0 entries are intentional (presence tracking), add a `note` column. If they're errors, add a `CHECK (amount >= 0)` constraint and flag existing zeros for review.

---

#### W6: `tasks` Table Schema Mismatch With JSON
The DB `tasks` table has a flat structure, while `tasks.json` uses `{open: [...], completed: [...]}` groups. They have different IDs, different row counts, and the DB `status` column uses `'open'/'completed'` while the JSON uses `'in-progress'/'pending'/'done'`. These two stores have completely diverged and can't be reconciled without a migration.

### 🔵 OPTIMIZATION

#### O1: Missing Indexes — Full Table Scans on Every Query
EXPLAIN QUERY PLAN shows `SCAN` (full table scan) for all non-agent tables:

| Query | Current Plan | Needed Index |
|-------|-------------|-------------|
| `WHERE night_id = ?` on srb_entries | SCAN | `CREATE INDEX idx_srb_entries_night_id ON srb_entries(night_id)` |
| `WHERE month = ?` on srb_nights | SCAN | `CREATE INDEX idx_srb_nights_month ON srb_nights(month)` |
| `WHERE date >= ?` on tesla_sessions | SCAN | `CREATE INDEX idx_tesla_date ON tesla_sessions(date)` |
| `WHERE owner=? AND status=?` on tasks | SCAN | `CREATE INDEX idx_tasks_owner_status ON tasks(owner, status)` |
| `WHERE artist_name=?` on artist_assets | SCAN | `CREATE INDEX idx_assets_artist ON artist_assets(artist_name)` |

At current row counts these are fast enough, but correct indexing is cheap insurance.

---

#### O2: WAL Mode Is ON — Good, But Checkpoint Not Optimized
```
PRAGMA journal_mode = wal       ← ✅ Good
PRAGMA synchronous = 2 (NORMAL) ← ✅ Good
PRAGMA wal_autocheckpoint = 1000 ← Default, fine for this workload
```
WAL + NORMAL synchronous is the right setting for this use case. The WAL file is 0 bytes (checkpointed). No changes needed here — this is actually well-configured.

---

#### O3: All Timestamp Columns Are TEXT, Not INTEGER
All tables use `TEXT DEFAULT CURRENT_TIMESTAMP` for timestamps. SQLite stores these as strings like `"2026-04-22T06:00:17.629559Z"` or `"2026-04-22 04:30:00"` — inconsistent formats. Date range queries on TEXT timestamps require string comparison, which works but is slower and format-sensitive.

**Fix:** Not critical to change now. For new columns, prefer `INTEGER` (Unix epoch) for timestamps. Add a note to development guidelines.

---

#### O4: `tasks.category` Is NULL for All 29 Rows
```
Tasks with NULL category: 29
```
The column exists, has a default of NULL, and no row has ever populated it. Either the UI never sets it, or it's vestigial. 

**Fix:** If unused, drop the column in the DB (and matching JSON field). If needed, add a NOT NULL DEFAULT 'General'.

---

#### O5: `agent_status_log` Will Grow Unbounded
The log has 12 rows now. No retention policy, no max rows, no cleanup job. At high update frequency it'll grow indefinitely.

**Fix:** Add a cleanup trigger or cron job that deletes log entries older than 90 days.

## 5. GitHub Backup Strategy Assessment

**Current state:**
- All `public/data/*.json` files are committed to GitHub repo `Animal71Animal/Mission-Control`
- Mutations go directly to GitHub via Contents API (PUT with SHA)
- No local backup of SQLite DB to GitHub
- The DB itself is **not version-controlled**

**Gaps:**
1. **DB not backed up** — if `mission-control.db` is lost (container wipe), agent status history is gone
2. **No atomic multi-record GitHub writes** — each mutation is a separate commit; concurrent writes can cause SHA conflicts
3. **No DB snapshot in git** — no recovery path if DB corrupts
4. **SRB nights/entries in DB only** — this data is NOT in GitHub JSON and is NOT backed up

**Fix:**
- Add a daily cron job to export `agent_current_state` and `agent_status_log` to `public/data/agent-status-snapshot.json` and commit to GitHub
- Add DB backup script: `cp mission-control.db backups/mission-control-$(date +%Y%m%d).db`
- Add SRB DB data export to `public/data/srb-db-snapshot.json`
